# Raid log manager

Keep one living log so the team knows what might go wrong, what has gone wrong, what is assumed, and what it depends on.

## Inputs to collect

Ask for what is missing, or mark it as unknown:
- Current project plan or status.
- Anything the user has just learned or worries about.
- The existing log, if there is one.

## Workflow

1. Classify each item correctly. A risk has not happened yet; an issue is happening now; an assumption is believed but unproven; a dependency is something the project needs from outside.
2. Write risks as cause, event, effect ('Because X, Y might happen, leading to Z').
3. Score likelihood and impact from 1 to 5 and multiply for a rating. Use the same scale throughout.
4. Choose a response for each risk: avoid, reduce, transfer or accept. Name an owner, a trigger to watch for, and a review date.
5. Turn any risk that has occurred into an issue, with an owner and a due date.
6. For each assumption, say how and by when it will be confirmed. For each dependency, name the supplier and the date needed.
7. Sort by rating, highlight the top five, and list items overdue for review.

## Output format

| ID | Type | Description | Likelihood | Impact | Rating | Response | Owner | Trigger / due | Next review |
|---|---|---|---|---|---|---|---|---|---|

Then a short summary: top five items, new this period, closed this period, overdue.

## Safety

- Do not hide or downgrade a risk to make the project look healthier.
- Do not name individuals as the cause of a risk; describe the situation.
- Keep sensitive commercial details to the people who need them.
